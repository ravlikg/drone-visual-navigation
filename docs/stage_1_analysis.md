## Що дає лекція і що з неї взято

| Розділ лекції | Що використано |
|---|---|
| Слайд 5–7: задача матчингу і 5-кроковий пайплайн Detect → Describe → Match → Filter → Estimate | Уся архітектура коду повторює ці кроки |
| Слайд 10: SIFT (DoG, інваріантність до масштабу й повороту) | Обраний детектор/дескриптор |
| Слайд 11: ORB, AKAZE (бінарні) | Реалізовані як альтернативи, порівняні в експерименті |
| Слайд 12: kNN + ratio test 0.7–0.8, FLANN, cross-check | FLANN kd-tree, ratio = 0.75, cross-check опційно |
| Слайд 13: гомографія, 8 DoF, плоска сцена | Модель «кадр → мапа» |
| Слайд 14: RANSAC, `cv2.findHomography(..., 5.0)` | MAGSAC++ (`USAC_MAGSAC`, згаданий на слайді 7), поріг 5 px |
| Слайд 23: правило вибору матчера | Обґрунтування SIFT як бейзлайну і чому ORB слабший |
| Слайд 25: Preprocess → Select region → Match → Verify → Georeference → Fuse | Покроково реалізовано в `localize.py` і `trajectory.py` (Fuse = Kalman без IMU) |

## Що НЕ взято з лекції і чому

* **DL-матчери (SuperPoint/LightGlue, LoFTR, RoMa).** На цих даних SIFT уже дає
  50/50 кадрів із похибкою 0,3 px, тож важкий DL-стек (PyTorch, ваги) нічого не
  додає. У README це описано як наступний крок для складніших пар.
* **Template matching / phase correlation** (слайд 15) потребують кадру, уже
  вирівняного на північ і в масштабі мапи, а тут кадри повернуті на 45–135°.
* **Переведення в lat/lon** (rasterio/GDAL): мапа звичайний PNG без геоприв'язки,
  тому координати даються в пікселях мапи.

## Аналіз даних (власне)

* Мапа 3645×1845 px, центр великого міста з річкою: багата текстура, добре для SIFT.
* Кадри 640×640, з іншої зйомки (інший колір/освітлення), повернуті. Масштаб,
  знайдений програмою, дорівнює 0,253: кадр приблизно в 4 рази детальніший за мапу.
* Ground truth не надано, тому якість оцінюється через RMSE репроєкції,
  візуальні накладання (`outputs/matches/`), узгодженість між конфігураціями
  і синтетичний тест із пропусками.
